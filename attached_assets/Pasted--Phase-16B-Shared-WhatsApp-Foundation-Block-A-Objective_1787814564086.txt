# Phase 16B — Shared WhatsApp Foundation + Block A

## Objective

Implement the minimum shared foundation required for the next FluencyJet WhatsApp automations, and implement ONLY Block A:

1. `fj_watch_lesson1_v1`
2. `fj_discover_learning_path_v1`

The existing production automation `fj_resume_lesson1_v1` / `LESSON1_SIGNUP_REMINDER` is already working with real users and MUST remain working.

This is an implementation task, not a broad architecture/audit task.

## CRITICAL SAFETY

The default Replit `DATABASE_URL` points to the REAL Railway production database.

`TEST_DATABASE_URL` is the isolated testing database.

NEVER run destructive or development migration operations against the default `DATABASE_URL`.

Do NOT:

* run `prisma migrate reset`
* reset any production schema
* delete or modify production customer data
* alter historical migrations
* rewrite migration history
* run destructive Prisma commands
* deploy to Railway
* push changes to production
* change Railway variables
* send any real WhatsApp messages
* run live/provider dispatches
* create another scheduler/cron
* create another WhatsApp provider implementation

If tests require a database, use `TEST_DATABASE_URL` explicitly.

Do not assume an environment command is safe merely because it is running in Replit.

## COST / SCOPE RULE

Do not perform a broad repository audit.

Inspect only the files needed to understand and implement:

* Prisma schema / relevant existing migrations
* AutomationEvent
* existing `LESSON1_SIGNUP_REMINDER`
* current automation worker/dispatcher
* current lesson progress update path
* Lesson 1 frontend/backend route
* curriculum/learning-path frontend/backend route
* existing cancellation/idempotency helpers
* relevant tests

Reuse existing patterns wherever possible.

Do not build generic automation infrastructure beyond what the current seven-message journey requires.

# 5. PRACTICE COMPLETION TRIGGER

Existing server-side lesson/mode progress is authoritative.

The first 10-sentence completion milestone must be created only when an accepted server-side progress update represents the first transition equivalent to:

previous completed < 10

to

new completed >= 10

for the relevant initial Lesson 1 practice.

Record:

`LESSON1_PRACTICE_COMPLETED`

exactly once.

Milestone recording must be idempotent and concurrency safe.

On the FIRST successful occurrence:

create exactly one:

`LESSON1_WATCH_REMINDER`

for the same learner/product.

Schedule:

approximately milestone occurrence + 15 minutes.

Also cancel an applicable still-pending:

`LESSON1_SIGNUP_REMINDER`

because the learner has completed the practice.

Do not delete its audit record.

If existing final eligibility already prevents the signup reminder after practice completion, preserve that protection as well.

Duplicate/replayed progress updates must not create duplicate milestones or duplicate automation events.

---

# 6. LESSON 1 OPENED DEFINITION

For this phase:

`LESSON1_OPENED` means:

The authenticated learner successfully enters/loads the actual Lesson 1 learning/content experience.

It does NOT require:

* video completion
* video percentage
* Vimeo analytics
* GA event
* Meta browser event
* watch-duration threshold

Add the minimum authenticated server-side milestone call necessary.

It should be safe to call repeatedly from the frontend; backend idempotency must make repeated calls harmless.

On first occurrence of:

`LESSON1_OPENED`

perform both:

### A. Cancel

Any applicable still-PENDING:

`LESSON1_WATCH_REMINDER`

for the same learner/product.

Do not delete the event.

### B. Create

Exactly one:

`LEARNING_PATH_DISCOVERY_REMINDER`

scheduled approximately:

Lesson 1 opened time + 75 minutes.

---

# 7. LEARNING PATH EXPLORED DEFINITION

For this phase:

`LEARNING_PATH_EXPLORED` means:

The authenticated learner deliberately opens the FluencyJet curriculum / learning-path experience.

No scrolling-depth, time-on-page or complex analytics threshold is required.

Add the minimum authenticated server-side milestone call.

Frontend may safely call it repeatedly.

Backend must persist the milestone exactly once.

When this milestone first occurs:

cancel any applicable still-PENDING:

`LEARNING_PATH_DISCOVERY_REMINDER`

for the same learner/product.

Do not delete audit history.

# 8. FINAL ELIGIBILITY — WATCH LESSON REMINDER

Before `LESSON1_WATCH_REMINDER` can enter provider dispatch, reuse the existing final locked eligibility system.

In addition to ALL existing common WhatsApp safety rules, final eligibility must confirm that:

* event still belongs to intended learner/product
* event is still eligible/current
* `LESSON1_OPENED` has NOT occurred
* destination snapshot remains valid
* WhatsApp consent remains valid
* learner is not STOP/suppressed
* no other existing safety condition makes dispatch inappropriate

If Lesson 1 has already been opened, do NOT send.

Cancel/skip using the existing audit-safe pattern.

# 9. FINAL ELIGIBILITY — DISCOVERY REMINDER
